# 后台一键获取地理位置兜底设计

## 目标

修复后台内容表单“一键获取地理位置”在浏览器定位失败时无法继续工作的体验，同时保留精确定位、照片 EXIF GPS 和手动填写能力。

## 现状与根因

当前表单直接调用浏览器 `navigator.geolocation.getCurrentPosition`。定位失败时统一显示“无法获取当前位置”，没有区分浏览器不支持、权限拒绝和超时，也没有备用来源。坐标获取成功后还要串行调用反向地理编码，因此地址解析失败也容易被用户理解为整次定位失败。

生产部署由 Cloudflare 代理 Vercel，Next.js Route Handler 仍在 Vercel 执行。Cloudflare 会通过 `CF-Connecting-IP` 传递访客 IP；DNS-only 或本地开发环境可能只有其他代理头，或完全没有公网 IP。

## 方案

### 定位优先级

1. 浏览器精确定位。
2. 浏览器定位失败后调用本站 `/api/geocode/ip`，由服务端使用 IP 地理服务返回城市和地区。
3. 两者都失败时保留表单手动填写，并给出可操作的错误提示。

照片 EXIF GPS 仍在选择照片后优先使用，不被一键定位覆盖，除非用户主动点击按钮。

### 服务端 IP 定位

新增 `GET /api/geocode/ip` Route Handler：

- 依次读取 `CF-Connecting-IP`、`X-Forwarded-For` 的第一个地址、`X-Real-IP`。
- 没有可用请求头时请求 IP 服务的自动识别入口；若服务无法识别则返回 502。
- 使用超时控制和 Zod 校验上游响应，只返回 `city`、`region`，不返回或持久化 IP。
- Cloudflare/Vercel 代理下优先使用 `CF-Connecting-IP`，避免把 Cloudflare 节点地址当作用户地址。

### 客户端行为

`getCurrentLocation` 返回带错误码的失败信息，并在调用前检查浏览器地理位置 API 是否可用。表单按钮执行以下流程：

- 精确定位成功：写入纬度、经度，切换为“公开精确地点”，再尝试反向解析地点名称。
- 精确定位失败：调用 IP 兜底；成功时写入城市、地区，切换为“仅城市和地区”，不填精确坐标。
- IP 兜底失败：不修改现有地点值，提示用户检查 HTTPS/权限或手动填写。
- 反向解析失败不影响坐标成功状态，单独提示“已获取坐标，请手动填写地点名称”。

按钮在请求期间禁用，避免重复请求；状态文本使用 `aria-live` 供辅助技术读取。

## 错误处理与隐私

- 浏览器定位仅在安全上下文（HTTPS 或 localhost）中可用；提示信息会明确指出这一点。
- IP 定位只提供城市级估算，不能满足“公开精确地点”的经纬度要求，因此成功后自动切换为城市级公开范围。
- 不在客户端暴露第三方 IP 服务地址，不在应用数据库记录 IP。
- VPN、移动网络和企业出口可能造成城市偏差，界面保留手动修正入口。

## 测试与验证

- 单元测试：浏览器定位成功、权限拒绝、超时、不支持；IP 响应成功/异常；Cloudflare 与其他代理头优先级。
- 表单测试：精确定位成功切换、IP 兜底切换城市级、两级失败不覆盖用户输入。
- 验证命令：`npm test`、`npm run typecheck`、`npm run build`、`git diff --check`。
